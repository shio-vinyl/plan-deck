# 设计原则

记录规则的来由，写页面时不用通读，具体做法以 `visual-language.md`、`page-types.md`、`humanize.md` 为准。前半部分是规划汇报的特点，也就是工具的出发点；后半部分是已定的设计决策及理由。改动决策前先和用户确认，确认后修订本文。

## 规划汇报的特点

规划汇报和其他 PPT（产品发布、咨询报告、学术答辩）的区别，下面九条在调研过的规划汇报里普遍成立。它们是工具的内建规则，不按体裁开关（决策 2）。

1. **地图是证据，不是插图。** 论断落在具体的地方，几乎每个内容页都有范围红线；同一张底图会连续用很多页，只换专题图层；比较时用同范围、同比例尺的多联图；重点地区页配定位小图。→ 地图槽位是一等公民，同组地图共享范围、画幅、比例尺和底图，翻页不跳动（决策 6，`map-types.md`）。
2. **数字是账，要对得上。** 面积、规模、指标之间有算术关系（“现状 − 调出 + 补划 = 规划”、用地平衡表合计 100%）；一份总规汇报常有几十个数值在多页重复出现，随工作推进反复修改，最容易出现新旧两个数并存。→ 数据唯一来源，检查跨页一致性和等式、合计（决策 10）；账算式、指标表、用地平衡表做成组件。
3. **正当性来自上位依据。** 逐级引用国家 → 省 → 市的政策、上位规划和规范；方案要说明落实了什么，偏离时逐条说明理由。→ 页面有依据 / 出处槽位，出处文字不能被版式吞掉；政策摘录、上位规划解读、调整说明都有对应页型。
4. **听众是审查者和决策者。** 主管部门、上级部门、本级政府逐页核对、最后拍板；页面也是会后留存的记录，单页 200–600 字很常见。结尾是“下步工作计划”“恳请支持事项”“敬请批评指正”，不是金句。→ 目标是“密而不乱”，不是“一页一观点、大字留白”（`visual-language.md`）；每页的量由结构大纲约束（决策 11）。
5. **它是过程文件，不是成品。** 封面写着阶段（初步方案、第 N 次汇报）；方案比选留给领导定；数据没到先留占位；相邻两版常有近一半页面原样复用；致谢页后藏着隐藏的备用页；改版时插一页分隔页、后接修订页，旧页不删；团队习惯把页面任务说明和暂存文字放在画布外；页面尺寸各项目不同。→ 页面池和占位是一等操作（决策 5，占位记在大纲里，不上页面）；pptx 是唯一真身（决策 4）；画布外对象的内容要能列全、不得误删、不当正文（决策 19）；页面尺寸是项目参数。
6. **有固定的话语体系。** 标题是“编号 + 类别 + 主题”，说明这页是什么，让结构一眼能看清；也可以是带事实的结果句（“更新潜力空间为 12.6km²”）；副标题默认不写；页面不用讲解员口吻（决策 13）；空间结构用数字概括（“一屏多廊、一带多点”）；动词是落实、构建、统筹、优化；列表讲对仗；问题用“问题 N”或问句提出再逐条回答；文件和规划写全称，不用“国空”这类简称。营销腔、咨询腔一看就不对。→ 措辞规则配正反例，写在 `visual-language.md`“页面文字”。
7. **结构是树，不是故事线。** 先分门类再逐项展开（现状分“空间基础 1–5”，问题再分 1）2）3））；先总后分（先一页列出全部问题或“三大策略”，再逐项展开）；页眉随时标出所在位置；同级节点颗粒度相近、句式相同；问题、目标、策略逐条对应。agent 默认的写法正好相反：按故事弧推进、有游离页、同级句式各异。→ 结构大纲，一个叶节点一页（决策 11）。
8. **内容受外部要求约束。** 讲什么由编制指南、上位规划、任务书和评审意见决定，而这些随项目、地方、时期变化；城市更新、体检评估、片区统筹这类工作也很难归入某种规划类型。→ 不内置按规划类型划分的内容清单（决策 2），结构初稿可以从项目材料里提取。
9. **是多人分头做、再拼起来的。** 同一份里页眉、标题位置前后不一；画布外留着分工条；页面在项目和版本之间流转。→ 视觉系统由工具保证全册一致（定稿后的去 AI 味版例外，决策 18）；工具生成的形状统一命名，人工元素不认识就不动；占位和页面任务有正式表达，取代画布外的手写条。

网格、统一的视觉系统、固定的标题层级、图示母题和节奏，是所有好 PPT 的共同做法，不是规划特有的；工具在这部分用通用设计方法（`visual-language.md`）。

## 决策

### 1. 目标是“规划院汇报的逻辑 + 国际咨询文本的视觉品质”

**决策**：叙事和页型以规划院自己的汇报为准；视觉品质向国际咨询文本看齐，但不照搬它的少字、口号式叙事。

**理由**：规划院汇报的逻辑是汇报对象需要的，它的视觉短板来自人力不足，而不是方向不对。国际咨询文本的品质主要来自一致的视觉系统和网格，这些是所有好 PPT 的通用做法，正好适合由工具承担。工具做出来过于整齐的问题，放在定稿后单独处理（决策 18）。

### 2. 不分体裁，以规划汇报的共性为内建规则

**决策**：不给 deck 定体裁。上面九条特点作为工具的内建规则，不设开关。密度和版式由页型决定；deck 层只记几项互相独立的事实：汇报对象和场合、所处阶段、页面尺寸和项目视觉系统（含用途：实用汇报或讲究美感，见 `visual-language.md`）。也不按规划类型内置内容清单：工具只管“怎么表达”，“讲什么”由项目材料和用户决定。

**理由**：规划汇报的差异主要出现在同一份汇报的页与页之间，而不是汇报与汇报之间：同一份总规汇报里，规模测算页几乎无图，地图页以图为主；总规的工作过程页和政策研究的框图页是一个样子。按体裁给整份汇报定风格，只能做出平均风格；前期调研时，体裁也越分越多（一轮就从 3 类变成 5 类）。用户此前做过按类型区分的尝试，效果不好。按规划类型内置内容清单同样会把内容提前锁死；使用者是规划师，漏讲法定内容不是他们的痛点。

（2026-10-25 修订，取代“体裁是顶层参数”。）

### 3. 不用母版文件，由规则生成项目模板

**决策**：不依赖 pptx 母版文件。每个项目开头定一次视觉系统，全册由“视觉系统 + 网格 + 页眉页脚 + 固定版式 + 组件”生成，效果上就是一套项目专属的模板。agent 只在这个框架里设计：从版式清单里选版式、往槽位里填内容，不自由摆放（`visual-language.md`）。定稿后另出的去 AI 味版例外（决策 18）。

**理由**：团队的汇报没有固定模板，最多只有页眉页脚，内容按业务自由发挥；agent 临时发明版式，一致性就差。由结构生成页眉页脚、由固定版式承载内容，既不需要现成模板，又能保证全册像一套。

（2026-10-26 修订，取代“没有模板，用版式语法”。）

### 4. pptx 是唯一真身

**决策**：出页脚本只用来**搭架子**（起稿、新增章节）。之后所有修改直接作用在 pptx 上：读取 → 按名字定位 → 局部修改。工具生成的形状统一命名；人工添加的元素不认识就不动。

**理由**：团队协作里，同事会直接在 PowerPoint 里改。如果重新生成，别人的修改会被覆盖。

### 5. 支持页面池和拼装

**决策**：一等操作包括：跨文件取页、重排、改写、隐藏为备用页、留占位页。占位记在结构大纲和交付说明里（“待补：规划用地图（等某某数据）”），页面上不写（决策 16）：缺的内容直接不写，也不放空图框。

**理由**：相邻两版常有近一半页面直接复用，致谢页之后常藏着备用页（特点 5）。规划流程不是线性的，文本和数据常常晚于汇报，占位是常态；但“待补”这类字样不是规划汇报的内容，用户看到页面上有就要求删（2026-11）。

### 6. 地图交给 gis 系列

**决策**：plan-deck 只定义地图槽位规格，并负责排版；分析交给 gis-kit，出图交给 gis-composer。图例、指标表、标注尽量做成可编辑的 pptx 元素。

**理由**：与现有 gis 系列的分工一致，各自可以独立迭代；可编辑的图例和表格便于团队修改。

### 7. 不绑定 harness

**决策**：机制全部放进独立 CLI；skill 文档只写工作流和判断规则；同一份说明 Claude Code 和 Codex 都能用。

**理由**：用户同时使用多个 harness；gis 系列已经验证了“独立运行时 + 薄 skill”的模式。

### 8. 输出必须可编辑

**决策**：交付物是原生 pptx，文字是文本框，表格是表格，框图是形状。PDF 只作附带。

**理由**：团队协作，后续要改。

### 9. 规则以规划汇报的实际做法和试做反馈为准

**决策**：版式、措辞、密度规则有两个来源：前期调研归纳出的规划汇报做法（已写进本目录各文档），以及试做中用户的反馈。两者都不支持的通用审美判断不进规则。不再维护外部案例库。

**理由**：前作的视觉规则来自通用设计审美，与规划院的实际做法有冲突（见“与前作的关系”）。案例库在前期用来理清思路，规律已经归纳完；之后真正暴露问题的是试做，用户的判断比继续扩充案例更直接。

（2026-10-25 修订，取代“规则以语料为准”。）

### 10. 数据有唯一来源，汇报只引用

**决策**：汇报里的统计数字、数值表、图表和地图，各有唯一的数据来源（文本、统计资料、GIS 数据等）；汇报引用来源，不手抄。来源变化后，工具要能找出所有受影响的页面和元素，并帮助更新、校验。数值以数据来源为准；版式和页面内容以 pptx 为准（决策 4）。

**理由**：关键数字贯穿全册、随工作推进反复修改，一改汇报就得跟着改，这是规划工作量的一大来源，也最容易漏改（特点 2）。

具体机制（数据登记方式、正文里手打的数字如何追踪、人工改过的绑定元素如何处理）还没有设计，见 Issue #10。

### 11. 每份汇报有一份结构大纲，一个叶节点就是一页

**决策**：汇报按结构树（章 → 节 → 条……）组织。分页只有一条规则：**每个叶节点做且只做一页**。一页放不下，说明这个节点要拆成下一级节点；内容太少，就与同级节点合并，由上一级节点做这一页。中间节点可以带一页总览，标题就是这个节点名，放在下级节点之前：例如“2.1 三大策略”一页列出三项，后面接 2.1.1、2.1.2、2.1.3 各一页；不需要总览时，中间节点不出页。一级标题自动生成章节页。封面、目录、章节页、致谢页、编号和页眉标题都由树决定，重排时重新编号。占位页同样是叶节点；隐藏的备用页放在树外的备用池里（决策 5）。

**页面标题就是节点名**，一字不差（含编号）；agent 想表达的判断放进正文或讲稿，不改标题，也不另写副标题。节点名默认是“编号 + 主题”，用户也可以写成论断句。

**理由**：早期规则让 agent 把论断写进副标题，结果每页都概括一句判断，读起来像 AI 写的，用户逐页删过（2026-11）。规划汇报靠结构清晰，标题连起来应当就是目录。带事实的结果句不同，真实汇报里很常见，它说的是页面证据得出的事实，不是解释。

结构树写成 Markdown 大纲，与 pptx 放在一起，每份 pptx 都有一份。大纲只记结构：节点名、页码，以及待补、备用等状态；内容只在 pptx 里（决策 4）。大纲由 agent 维护，人只看不改：起稿时先写大纲，连同一份一次性的页面计划（逐页写讲什么、用哪些材料、选什么页型和版式）交用户过目，再按大纲出页，出页后页面计划不再维护；之后每次修改 pptx 都同步更新大纲；没有大纲的 pptx，先从标题、面包屑、目录反推出大纲。用户对着大纲指挥 agent 改 pptx。agent 不得自行改动节点名、层级和顺序，拆分或合并节点也要先问用户。格式见 `architecture.md`。

一页太满还是太空，由用户判断，agent 协助：出页时发现哪些页可能放不下或内容偏少，主动停下来列给用户，问是否拆分或合并；不得靠缩小字号、删减内容或拉大留白来凑。

树的枝（现状分哪几方面、分析从哪几个角度）由项目决定，可以用文本目录作初稿；工具只要求形式清楚：同级平行、先总后分、编号连续、跨章对应可查。页眉显示上级和本页两级标题，树的深度不设上限。

**理由**：规划汇报按门类层层展开，本质上就是分级标题，每页对应一个标题（特点 7）；agent 默认的写法恰好是故事线式的。试做 01 里，agent 自己决定怎么分页，还会把标题改得偏离原意；把页面标题钉在节点名上，结构就由人掌握。“一个叶节点一页”把每页的信息量交给结构来约束：太满就拆，太空就合。动辄上百页的汇报，人对着大纲才捋得清结构，指挥 agent 修改也更准确。手工维护编号、页眉和目录，也是重排页面时的主要负担。

（2026-10-25 修订，取代“起稿先出结构树，用户确认后再生成页面”。）

### 12. 工作稿、去 AI 味版和交付副本分开

**决策**：改稿说明、待确认、隐藏备用页留在工作稿里，方便继续改。用户确认定稿后另存去 AI 味版（决策 18），工作稿保留，以后的内容修改先改工作稿。文件要发给别人时，用 `plan-deck clean` 另存交付副本，页面不动，备注里的过程信息清掉。隐藏页默认保留，要不要删单独问用户。

**理由**：过程文件的特点（特点 5）要求保留这些信息，但备注和隐藏页对方打开文件就能看到（2026-11，用户要求清备注；删掉隐藏页后又要求加回）。串页的讲稿要对照页面判断归属，工具只列出来，不自动删。去 AI 味费时间，版面又难以逆向改回，所以和工作稿分开（2026-11，用户要求两版都留，方便以后协作）。

### 13. 页面不当讲解员

**决策**：页面是被讲的材料，只呈现内容；解释、串讲、点明重点的事由汇报人来做，放在讲稿里。判断方法：这句话在说项目和政策本身，还是在告诉读者这页讲什么、该怎么看？后者不上页面。规则见 `visual-language.md`“不当讲解员”。

**理由**：改稿中用户否定的写法，表面上各不相同（解释性的标题和副标题、“要解决什么”这类小标题、“怎么查”这类读法说明、“不是 X，是 Y”），实际都是在对读者说话（2026-11）。禁用词表挡不住，讲解员能换无数种说法，所以定成原则，词表只作例子。对照真实汇报：页内小标题几乎全是名词（城市问题、更新方向、基本情况、权属情况），讲解口吻的只占 0—1%，试做稿占 6%。听众是逐页核对的审查者（特点 4），他们要的是能核对的内容。

### 14. 版面的分量来自内容和实色，不来自卡片

**决策**：规划汇报的层次靠证据物（地图、案例图、文件摘录、表、原生图表）和图示；图示节点可以用实色块，直角、不加阴影，箭头线要和节点分量相称。整块实色的卡片看时机可以用（并列的同类内容，颜色表示类别）；不用阴影、描边加显著的卡片，也不走大留白的极简路线。

**理由**：对 8 份真实汇报和试做稿的统计（2026-11）：框内文字占比、圆角、阴影都区分不出 AI 味，手做稿里这些都很常见；区分力最强的是同排等尺寸模块的页（手做稿 1%—7%，用户判为有 AI 味的页 45%）和大图页（手做稿 18%—71%，这些页 0）。逐档样张的用户判断：实色节点加证据物最顺眼；阴影加卡片太土；瑞士风撑不起每页三四百字的内容量；细箭头有 AI 味；小结页并列的四个机制用整块色卡片是可以的。

### 15. 每页三层

**决策**：内容页一般有三层：一行红字结论（带事实的判断），放大的重点（整块实色、大字、粗箭头），密集的次要信息（12—14 磅，条款、时间、数字、案例、程序都留着）。连续的清单页可以省红字；去 AI 味版里红字不必每页同一位置、同一形式（决策 18）。写法见 `visual-language.md`“每页三层”。

**理由**：用户看试做稿后要求页面要有观点，重点要大胆强调，同时次要信息不能删少（2026-11）；这一条取代此前“页内不放大字主句”的规定。此后统计发现试做稿 93% 的页都有同样的红字行，人做的稿子只有 8%—33%，也让每页长得一样，用户因此定下不必每页同形（2026-11）。

### 16. 页面不写核查和防御用语

**决策**：核查和防御用语（清单见 `visual-language.md`“页面绝不出现”）绝不上页面。缺的内容直接不写；核实结果、适用范围的澄清、保留意见放备注或交付说明。性质说明（假设情形、按指南推演）只放三级标题。

**理由**：这些是写的人给自己看的，不是规划汇报的内容（2026-11，用户明确要求写进 skill）。子会话最容易把讨论定下的口径直接写上页面，所以派活时要带上（`SKILL.md`“给子会话派活”）。`inspect` 和 `audit` 都查这些词，报为问题、影响退出码（2026-11 起，用户要求严格控制，清单与 GIS 系列统一）；讲解员口吻误报多，仍只警告。

### 17. 省虚词，不省用地类型、对象和主体

**决策**：汇报文字用规划语言：动词用双音节，缩略只用文件或行业已有的说法，不为省字现场造词，条目记法不进叙述句。放不下时少说一件事，不压词。规则见 `visual-language.md`“省略和用词”。

**理由**：用户和同事都认为 AI 味主要在语言习惯，有些省略让人看不懂或看着怪。逐份对照（2026-11）：句子短本身不是问题，试做稿的分句长度和人写稿差不多；“一个字动词＋术语”试做稿每万字 57 处，人写稿和政策文件 1—12 处；“走规划修改”这类口语试做稿 32 次，五份参照 0 次；制度动词和连接关系词的密度只有人写稿的一半左右，分寸词则没有差别。红字结论约一半是把本页内容压成一行的三段并列。

### 18. 去 AI 味放在定稿后，单独出一版

**决策**：默认不做。用户确认定稿后才做，同时保留未去的工作稿。内容页做第 2 档（换色加按内容定形）；不加红虚线框、框字小红框、大箭头、图压字这类刻意的标注（2026-11，用户试看全册后定）。这一版的一致性分两层：页眉、标题层级、字号下限、页码、红色表示重点保持一致；配色、模块尺寸、线型、页面骨架放开，放开的程度以用户认可的分档样张为准。放开只用于这一版，工作稿仍按 `visual-language.md` 的一致性规则。配图属于内容阶段，不算去 AI 味。流程和做法见 `humanize.md`。

**理由**：用户觉得 AI 稿“过于整齐、讲审美”。逐页统计（2026-11，`humanize.md`）：差别不在颜色数和留白，而在颜色调和成一家、框等尺寸、连续同版面和图少。第 1 档只换色不够。这个做法不是随机弄乱：颜色按内容分类，并列的内容才等宽。做一次很费时间，内容没定时做了也白做，也不方便看内容，所以放在最后；同事之后还要协作，所以两版都留。

### 19. 版面外是资料；内外两版对不上时以版面内为准

**决策**：版面外的内容要读，但不当正文。同一内容在版面内外各有一版、数字对不上时，默认以版面内为准，版面外视为旧版或暂存，不用逐条问用户。工具把同结构表格的差异列为线索，不删、不改版面外的内容。

**理由**：版面内的才是决定用的，不然也不会放到外面。真实稿子里常见的情形：版面上一张分区统计表是采用版，版面外一张同结构、个别数字不同的表是改之前的旧版。

**边界**：这条只决定内外冲突时用哪版。版面外独有的资料仍要列出来，判断后再用；不同文件、不同材料之间对不上的数字仍要问用户。

### 20. 正文做法和页眉预设进运行时

**决策**：放大的重点常用的几种做法（标签行、实色栏头并列、结论通栏、箭头链和节点链、泳道、文件摘录、矩阵表、分档台阶）做成组件：按内容定高，默认铺到版心底，按颜色名取色，放不下就警告。通栏页眉、字号阶梯和按含义命名的配色做成预设，用 `style init` 生成。检查补上未铺满、缺中间层、箭头压字、标签行过多、按色相命名和同色异义。做法和使用场合写在 `patterns.md`。通栏页眉的章名行是页眉的一行，和正文同字号，不算页角标签；用这个预设时页码从工作稿起就有。字号级差在小标题以上放宽到约 1.15 倍。

**理由**：对照两份 AI 做的工作稿（2026-11）：一份的做法写在项目脚本里，正文约两成是 14 磅以上的字，未铺满的页约 3%；另一份只用了运行时已有的正文、表格和账算式，这两项是 14% 和 7%。规则文档一样，落实不一样。能力弱的模型和别的宿主也会用这个 skill，读了规则不一定做得到；放进运行时，默认值就是对的，做偏了有警告。参照稿的这些做法在工作稿和去 AI 味版里都有，所以进工作稿的默认；去 AI 味版的配色和定形不进（决策 18）。参照稿页眉的节名 26 磅、红字结论 22 磅只差 1.18 倍，用户认可这套页眉，所以放宽级差。

## 与前作的关系

前作是作者 2026 年 4 月写的一个 Codex skill 加 Python CLI（未公开），实现过 pptx 的 inspect / 对象查询 / patch / validate，以及按命名对象定位和网格摆放，与决策 4 的方向一致。现在的运行时没有依赖它（依赖只有 python-pptx、pillow）；做页面池操作时可以再参考。

它的视觉规则（黑白灰加一个强调色、每页一个主要观点、避免装饰卡片）来自通用设计审美，适用于国际咨询文本和学院派评图，但与规划院汇报不符：规划院汇报常用多色框图和高密度页面，这是汇报对象习惯的表达方式。不过这些框是图示的一部分，不是正文的容器（`visual-language.md`“框和卡片”）；前作“避免装饰卡片”在“不用框包正文”这一点上与实际做法一致，不一致的是它把框图一并排除。
